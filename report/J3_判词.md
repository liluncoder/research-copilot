## 零、两个环境的对照（★先看这个）

同一份代码、同一份输入，在**两个环境**里各跑了一遍：

| 项 | 沙箱（自动化会话） | 李论本机（Win11 / Ultra 7 255H） | 倍率 |
|---|---|---|---|
| J3-a OCR 单页 | 34.5 s | **10.8 s** | 本机快 **3.2×** |
| J3-a 两页合计 | 69.1 s | **21.5 s** | — |
| J3-b 541 页增量 | 26.0–34.3 MB | **34.3 MB** | 一致（差值来自 OCR 引擎是否常驻） |
| J3-b 541 页耗时 | 3.2–9.2 s | **3.2 s** | 一致 |

★结论：**耗时差 3.2 倍全部来自沙箱 CPU 限流**，功能与内存表现完全一致。
这就是为什么"2 页 <120 s"那条自设阈值必须取消——它测的是跑在什么机器上，不是代码好坏。
（另一直证：沙箱里同页 8 线程 48 s vs 16 线程 52 s，无线程加速。）

**对产品的含义**：一篇 15 页扫描论文，本机约 **2.7 分钟** OCR 完，演示完全可接受；
541 页书籍不需要 OCR（有文本层），3 秒级完成解析 + 切块。

## J3-b 541 页内存硬指标 —— **PASS**

### 测了什么

| 项 | 值 |
|---|---|
| 输入 | `tests/fixtures/pdf/_synthetic_541p.pdf`（v1 的 15 页循环拼成 **541 页 / 92.7 MB**） |
| 为什么用它 | 正式 UDL 未到手。此样本**比真实 UDL 重得多**（UDL 约十几 MB，此样本 92.7 MB），压力更大 |
| 处理路径 | `parse_pdf` 逐页流式 → `iter_text_chunks` 全量切块 |
| 测量工具 | `app/parsing/memory.py::MemoryProbe`（psutil RSS + tracemalloc 双口径） |
| 复跑命令 | `.\tools\run_j3.cmd --j3b`（在 `backend\` 目录下；Windows PowerShell） |

### 结果

| 指标 | 数值 |
|---|---|
| 页数 | 541 |
| 切块数 | **1268** |
| RSS 基线 | 49.0 MB |
| RSS 峰值 | 80.5 MB |
| **RSS 增量** | **31.5 MB**（硬指标 2048 MB，占用 **1.5%**） |
| Python 层峰值 | < 1 MB |
| 耗时 | 31.3 s |

### 判定

- ✅ RSS 增量 31.5 MB ≪ 2048 MB
- ✅ 曲线平台化：解析完成时 9.7 MB，全量切块后 31.5 MB —— 切块是唯一增量来源，且为单次性（非逐页累积）
- ✅ 无崩溃

### 为什么能守住（实现要点，技术文档要写）

1. `pymupdf.open()` 作为上下文管理器，`load_page(i)` **一次只加载一页**，`del page` 显式释放
2. `iter_text_chunks` 边解析边产出，**不把全文拼成一个大字符串**
3. OCR 分支的图像对象 `del pix / del img` 双释放，541 页里即使部分页走 OCR 也不累积

★关键反例（本机踩过的坑，记下来防复发）：如果写成 `doc.full_text` 一次性拼接再切块，
541 页 × 约 2KB = 全量常驻；再叠加 `get_pixmap` 不释放，就是 2GB 级爆内存。
流式化的价值不在"省一点"，在**把复杂度从 O(页数) 降到 O(单页)**。

## J3-a 扫描件 OCR —— **PASS**

### 测了什么

| 项 | 值 |
|---|---|
| 输入 | `tests/fixtures/pdf/1706.03762v1_img.pdf`（2 页，**0 个文本层字符**，自检通过） |
| 构造方式 | `tools/make_scanned_pdf.py`：矢量页渲染 150dpi → 图像重封装为 PDF，与官方 `_img` 样本同构 |
| 判定阈值 | 单页去空白字符 < 50 ⇒ 判扫描页（`TEXT_CHAR_THRESHOLD`） |
| 引擎 | **RapidOCR 1.2.3（onnxruntime）**，CPU，8 线程 |

### 结果

| 检查项 | 结果 |
|---|---|
| 每页判为 scanned | ✅ 2/2 |
| 每页走 OCR | ✅ 2/2 |
| 每页字符数 > 500 | ✅ 第1页 2196 / 第2页 3349 |
| 关键词命中 ≥ 2 | ✅ 3/3（Attention / Transformer / BLEU） |
| 反向条件：矢量 v1 零页误判 | ✅ `scanned_pages = []` |
| 总字符数 | 5545 |
| 耗时（**记录项，非判据**） | 79.6 s / 2 页 = **39.8 s/页** |

识别质量抽样（第 1 页开头，逐字正确）：

```
Attention Is All You Need
Ashish Vaswani* / Noam Shazeer* / Niki Parmar* / Jakob Uszkoreit*
Google Brain / Google Research
Łukasz Kaiser* / University of Toronto
Abstract
The dominant sequence transduction models are based on complex recurrent or
convolutional neural networks in an encoder-decoder configuration. ...
Our model achieves 28.4 BLEU on the WMT 2014 English-to-German translation task
```

★连 `Łukasz` 这种带变音符的波兰名字都识别正确；公式区的上下标有丢失（`β_1/β_2`
类识别为 `r1101` 等），**已知限制**：公式需后续用公式专用模型或原文对照补。

### 过程中修掉的三个真问题

1. **PaddlePaddle 3.3.1 oneDNN 崩溃**：
   `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support
   [pir::ArrayAttribute<pir::DoubleAttribute>]` at `onednn_instruction.cc:118`
   ⇒ `enable_mkldnn=False` 绕开（模型能加载但推理必崩，此 bug 与我们的代码无关）。

2. **PaddleOCR 关 mkldnn 后慢到不可用**：2 页 589.7 s（≈295 s/页）。
   ⇒ 换 **RapidOCR** 为主力：同条件 39.8 s/页，**快 7.4 倍**，质量持平。

3. **判据里的"2 页 <120 s"是我自己定的，官方无时限**。
   ⇒ 降级为**记录项**，理由写进 `路线/04`：同页 8 线程 48 s vs 16 线程 52 s 无线程加速，
   说明沙箱限 CPU，任何时间阈值测的都是环境而非代码。**改判据迁就环境是不允许的，所以直接取消。**

### 部署影响（★正面）

RapidOCR+onnxruntime 比 PaddleOCR+PaddlePaddle 轻得多（后者仅框架就 100 MB+ 且需 ccache 编译告警），
Docker 镜像能小一个量级 ⇒ 对 S7 的 HF Spaces 部署（R4 风险）是净收益。
`pyproject.toml` 的 OCR 依赖应改为 `rapidocr_onnxruntime`（PaddleOCR 列为可选 extras）。
