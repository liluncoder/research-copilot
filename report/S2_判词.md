## 三、★当前用的是哪档向量：**hash（离线兜底），不是 BGE-M3**

原因：沙箱下载 ~25~125 KB/s，BGE-M3 权重 2.2GB、torch 约 200MB，本轮跑不完。
所以代码里做了**可插拔三档**，并且**不允许静默降级**：

| 档 | 用途 | 本次 |
|---|---|---|
| `bge-m3` | 产品形态，中文问题 → 英文论文的跨语言检索 | 未就绪（模型下载中） |
| `hash` | 零依赖确定性向量，用于验证**管线**是否正确 | ✅ 本次实测 |
| `auto` | 先试 bge-m3，失败退 hash，并把 `fallback_reason` 写进接口响应 | ✅ 当前生效 |

★**这两件事必须分开验证**（本项目最重要的一条方法论）：
"检索管线对不对"是逻辑问题，"向量质量好不好"是模型问题。
混在一起时，模型下不来 ⇒ 判据假失败，或者反过来悄悄降级 ⇒ 判据假通过。
所以接口返回里有 `backend.embedding` 字段，判词必须写清楚这次用的是哪档。

## 四、实现要点（技术文档要写的创新点）

1. **结构化切块**而非定长切块：以标题树为边界，每块带 `section_path / page_start / page_end`，
   检索命中后**天然能说出"哪一页哪一节"**——这是 J4 出处锚点的前提。
   章节过长才在**段落边界**切开，绝不在句子中间切；相邻块保留 120 字重叠防切口效应。
2. **RRF 融合**而非分数加权：Dense 余弦（0~1）与 BM25 分数（0~30+）量纲不同，
   加权要调参且不稳；RRF 只看名次（`Σ 1/(60+rank)`），零调参。
3. **稀疏通道不是装饰**：J4 的三连问全是"精确事实"（P100 / 0.98 / 28.4），
   向量对数字和专名不敏感，实测 R4 的 top1 就是靠 BM25 顶上去的。
4. **索引可插拔**：Chroma（装了就用）与 numpy 精确余弦（未装时）结果等价，
   保证评委环境不装 Chroma 也能复盘判据。

## 三、关键设计（技术文档重点）

1. **查询改写是这条链的命门**，不是装饰：
   判据问的是**中文**，论文是**英文**；当前向量档还是 hash（没有跨语言能力）。
   实测 Q1 原始中文问句几乎召不回目标段，靠 `plan` 节点改写成
   `Adam optimizer beta1 beta2 epsilon hyperparameters` 之后 top1 才落到 `5.3 Optimizer`。
   ⇒ 这一层同时解决"跨语言召回"和"口语 → 术语"两个问题，换 BGE-M3 后仍然有用。
2. **两道反幻觉闸**：
   ① 检索为空 ⇒ **直接拒答，连 LLM 都不调**（少一次编造机会）；
   ② 回答生成后逐条核对出处——文件名 + 页码必须能在本次检索结果里找到，
      对不上就剔除并计入 `invalid_citations`（不留在回答里冒充证据）。
   Q4 就是这么过的：模型想答"库里没有的东西"，检索层先空，答都不用答。
3. **状态机可换引擎**：同一组节点，装了 langgraph 就走 `StateGraph`，没装就走顺序执行器，
   `orchestrator` 字段如实返回本次用的是哪个 —— 判据不会因为环境差异而"看起来过了"。

## 四、已知限制（如实写进技术文档）

1. Q2 的出处落在 `6.1 Machine Translation` 而非 `5.2 Hardware and Schedule`：
   两个段都提到 P100，检索取了后者所在块。**事实正确、页段正确，但章节名不是最精确的那个**。
   属于"段落级锚点够用、句子级锚点还不够"的边界（`路线/02` 已把这条列为可接受）。
2. 向量档仍是 hash：中文直接检索能力弱，靠 plan 改写兜住；换 BGE-M3 后需复跑本判据。
3. LLM 依赖网络：沙箱到 DeepSeek 通，但 HF 下载不通 —— 两个通道状态不同，不要混为一谈。
